# Tauri macOS arm64 Packaging Design

## Goal

Produce a reproducible, locally installable macOS arm64 build of Ineed DevTool
from the Tauri runtime. The Electron runtime remains available for development,
compatibility checks, and cross-runtime transport acceptance, but is not a
distribution target in this phase.

This phase produces unsigned local artifacts. It does not claim public macOS
distribution readiness because Apple signing and notarization credentials are
not available.

## Approaches Considered

### Tauri official bundler (selected)

Enable the existing Tauri 2 bundle configuration and use `tauri build` to
produce the application bundle and disk image. This keeps packaging metadata in
the framework-owned schema, minimizes custom tooling, and preserves a direct
path to future signing, notarization, and additional operating systems.

### Custom DMG tooling

Build the `.app` with Tauri and assemble the disk image with separate shell or
Node tooling. This offers more presentation control but adds another packaging
dependency and duplicates validation already owned by the Tauri bundler. It is
not justified for the first local release.

### Dual Electron and Tauri distribution

Package both desktop shells. This would double installer, signing, upgrade, and
release verification work without adding user-facing functionality. Electron
therefore remains a tested secondary runtime rather than a release artifact.

## Scope

The implementation will:

- enable Tauri bundling for macOS;
- target Apple Silicon (`aarch64-apple-darwin`);
- emit an `.app` bundle and `.dmg` installer;
- retain product name `Ineed DevTool`, version `0.1.0`, and bundle identifier
  `com.ineedfull.dev-tool`;
- add a root command that builds the macOS package from a clean checkout;
- add a deterministic artifact verifier;
- launch and inspect the packaged application in production mode; and
- rerun the existing Phase 05 verification gate.

The implementation will not:

- package Electron;
- sign or notarize the application;
- configure automatic updates;
- publish artifacts to a remote service;
- add Windows, Linux, or Intel macOS targets; or
- change transport, persistence, workspace, or UI behavior.

## Configuration

`apps/tauri/src-tauri/tauri.conf.json` remains the authoritative application
metadata source. Bundling will be active with macOS application and DMG targets.
The existing icon remains the source asset unless the bundler proves it does
not satisfy macOS bundle requirements; any derived icon generated by official
Tauri tooling must be committed and verified.

The build must use the installed Rust target reported by `rustup target list
--installed`. The release command fails with an actionable message when
`aarch64-apple-darwin` is unavailable instead of silently producing a host-
dependent artifact.

## Commands And Artifacts

The repository root exposes one packaging entry point, `npm run package:mac`,
which delegates to the Tauri workspace. The command builds the production
renderer and native application for `aarch64-apple-darwin` and requests the
official app and DMG bundles.

A separate `npm run verify:package:mac` command validates already-built
artifacts without rebuilding them. It locates artifacts under the target
triple's release bundle directory and rejects missing, duplicate, empty, or
unexpectedly named results.

Expected products:

- `Ineed DevTool.app`
- one versioned or product-named `.dmg` containing the application

No artifact path is hard-coded outside the verifier's Tauri target-root
resolution.

## Artifact Verification

The verifier uses macOS and repository toolchain commands to assert:

- the `.app` and `.dmg` both exist and are non-empty;
- the executable exists inside the application bundle;
- the executable architecture includes `arm64` and excludes Intel-only output;
- `CFBundleIdentifier` is `com.ineedfull.dev-tool`;
- `CFBundleShortVersionString` is `0.1.0`;
- the display/product name is `Ineed DevTool`;
- the bundle has an icon resource referenced by `Info.plist`;
- the build emitted Tauri codegen assets from the production `frontendDist`;
  those assets are embedded in the native executable rather than copied as
  loose files under `Contents/Resources`; and
- the package is explicitly reported as unsigned when `codesign` finds no
  valid signing identity.

Unsigned status is informational for this phase. Every other mismatch fails
the command.

## Packaged Application Smoke Test

After artifact verification, the `.app` is launched directly from its bundle.
The smoke test confirms:

- a nonblank `Ineed DevTool` main window opens in the Tauri runtime;
- the embedded production renderer loads without a Vite server or loose
  `index.html` resource;
- the existing endpoint list loads from the production persistence path;
- endpoint filtering, settings, about, history, and sidebar controls render;
- serial, TCP, and UDP endpoint forms expose their production fields;
- invalid endpoint input is rejected without saving test data;
- no development Vite origin is used;
- the application exits normally; and
- no repository-owned application, Vite, or acceptance process remains.

The smoke test does not open user endpoints, alter saved settings, delete local
data, or install the DMG into `/Applications`. Direct bundle launch is enough to
verify the packaged production runtime without mutating system application
state.

## Failure Handling

Packaging and verification commands use nonzero exits for missing targets,
bundler failures, absent artifacts, metadata mismatches, wrong architecture,
or failed launch. Verification output identifies the failed invariant and the
artifact path involved.

The smoke-test process is always stopped after inspection. Cleanup checks are
scoped to this repository and package so unrelated Vite or desktop processes
are not terminated.

## Verification Sequence

1. Run focused configuration and verifier tests before changing packaging.
2. Build the Tauri macOS arm64 package.
3. Run the artifact verifier against the generated `.app` and `.dmg`.
4. Launch the packaged `.app` and complete the production smoke test.
5. Run `npm run verify:phase-05` from the final source revision.
6. Confirm a clean Git worktree and no repository-owned residual processes.

## Deferred Release Work

Apple Developer ID signing, notarization, stapling, automatic updates, remote
artifact publication, CI runners, dependency-security gates, complete history
export, and other operating-system targets remain separate follow-up projects.
They must not be represented as complete by this local unsigned packaging phase.
